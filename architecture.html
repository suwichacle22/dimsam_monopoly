Dimsam Monopoly: how to build and host it

Two players, cloud hosted, no monthly bill. Written for someone building their first multiplayer web game.

Short answer: don't host on your PC. Use a free cloud tier. Your PC still works for development.
  • Your PC as the host is possible (Cloudflare Tunnel or Tailscale make it free) but the game dies whenever the PC sleeps, reboots, or your home internet hiccups.
  • A two-player board game is tiny. It fits inside the free tier of every serious provider with a lot of room to spare.
  • Recommended: a static frontend on Cloudflare Pages or Vercel, game logic and realtime state on Convex, a room password only you two know.
  • Nothing here needs a credit card.

1. What a multiplayer web game is made of

Every online game, from Monopoly to a shooter, has these three parts. The questions you asked are about where part 2 and 3 live.

Your phone / laptopruns the browser. Draws the board, shows buttons.
⇄
Game serverthe referee. Rolls dice, checks rules, decides who owns what.
⇄
Girlfriend's phonesame browser app, sees the same board.
⇅
Databaseremembers the game so a page refresh or a dead phone battery doesn't lose it.
Why the dice must roll on the server, not in the browser
Anything that runs in the browser can be edited by the person holding the browser. If the dice roll happens on her phone, she could (in theory) always roll a 6. The server is the one place neither player controls, so it is the referee. In practice with Convex this means a tiny function called rollDice that runs on their machines, not yours.

For a couples game you probably trust each other. But the server-authoritative design is also what keeps both screens in sync, so you want it anyway.

3. Recommended stack, layer by layer

Frontend
React via TanStack Start + Vite + Tailwind CSS. The board, dice animation, property cards. Runs in the browser.
Hosted on Cloudflare Pages (free, unlimited bandwidth) or Vercel Hobby (free).
Backend + DB
Convex. You write TypeScript functions (rollDice, buyProperty, endTurn). Convex runs them, stores the tables, and pushes every change to both browsers live.
Free plan: roughly 1M function calls and 0.5 GB of data per month. A full Monopoly game is a few hundred calls.
Access control
A single room password stored as a Convex environment variable. Every function checks it. No signup screen, no OAuth, nothing to maintain.
Free. If you later want real accounts, Convex Auth is also free.
Domain
Use the free *.pages.dev or *.vercel.app URL. Nobody will guess it, and the password guards it anyway.
Free. A custom domain is optional, about $10/year.
Dev machine
Your PC runs bun dev and npx convex dev while you build. Convex gives you a separate dev deployment so you can break things without touching the live game.
Free.
Why Convex instead of writing my own Node + Socket.io server?
A hand-written server needs a machine that stays on, a WebSocket layer, reconnect logic, a database, and a deploy pipeline. For a first project that's four problems you didn't ask for. Convex is one problem: write a function, call it from React, the UI re-renders when data changes. If you outgrow it later, the game logic is plain TypeScript and moves anywhere.

Alternatives in the same spirit: Supabase (Postgres + realtime, free tier) or Firebase (Google, free Spark plan). Both work. Convex is the smoothest for "the UI must update the instant she clicks."

Where do the board tiles (names, prices, rents) live?
Not in the database. They never change, so they're a plain TypeScript array in a shared file, e.g. board.ts, imported by both the frontend and the Convex functions. Swap the street names for Doraemon locations (Nobita's house, the empty lot, 22nd century) in that one file and both sides agree.
Example Convex function (the whole "buy property" rule) 
export const buyProperty = mutation({
  args: { gameId: v.id("games"), password: v.string() },
  handler: async (ctx, { gameId, password }) => {
    if (password !== process.env.ROOM_PASSWORD) throw new Error("nope");
    const game = await ctx.db.get(gameId);
    const player = await ctx.db.get(game.currentPlayerId);
    const tile = BOARD[player.position];
    const prop = await ctx.db.query("properties")
      .withIndex("by_tile", q => q.eq("gameId", gameId).eq("tileIndex", player.position))
      .unique();
    if (prop.ownerId || player.cash < tile.price) throw new Error("can't buy");
    await ctx.db.patch(player._id, { cash: player.cash - tile.price });
    await ctx.db.patch(prop._id, { ownerId: player._id });
    await ctx.db.insert("events", { gameId, text: `${player.name} bought ${tile.name}`, at: Date.now() });
  },
});

Both browsers subscribe to the game. The moment this runs, both re-render. No socket code anywhere.

7. Build order

  1. ScaffoldTanStack Start + Tailwind via Bun. Add Convex. Get "hello" showing in the browser and one Convex query returning data. Half a day.
  2. Board data + static boardWrite board.ts with 40 tiles. Render the square board with CSS grid. No logic yet. Make it look like Doraemon.
  3. Lobby + room passwordCreate game, two players join by name, password checked on every call. Both screens show the same lobby.
  4. Core turn loopRoll (server-side), move, land, buy or pay rent, end turn. Skip chance cards, jail, houses for now. This is the moment it becomes a game.
  5. The rest of the rulesJail, doubles, chance and community chest, houses and hotels, mortgage, bankruptcy. Each one is a small Convex function.
  6. Deploynpx convex deploy for the backend, push to GitHub, connect Cloudflare Pages. Send her the link.
  7. PolishDice animation, piece movement, sound, a "whose turn" banner, Doraemon gadgets as chance cards.

8. Things that trip up first-timers

Keep all rules on the server, the UI only sends intent
The browser never says "set my cash to 2000". It says "I want to buy". The server decides what that means. This one habit prevents 90% of multiplayer bugs.
Mobile first
You will both play on phones. Design the board for a portrait screen from day one. A 40-tile square board is cramped on a phone; a common trick is a scrollable board with a zoomed "where am I" strip at the bottom.
Reconnect is free with Convex, but a page refresh must restore everything
Store the game id and player id in localStorage so a refresh lands you back in the same game as the same player. Don't keep any game state in React state only.
Doraemon art is copyrighted
For a private game between the two of you nobody cares. If you ever publish it, swap in your own drawings. Keep assets in one folder so that's a one-day job, not a rewrite.
Don't put the room password in frontend code
Type it on a login screen, keep it in localStorage, send it with each call. Anything compiled into the frontend bundle is public.
